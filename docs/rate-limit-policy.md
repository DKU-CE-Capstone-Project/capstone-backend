# 요청 한도 및 429 응답 정책

2026-10-25 기준 코드의 기본값과 동작이다. 운영 환경변수로 바꿀 수 있는 수치는 아래 설정명을 따른다. 팀의 트래픽·공급자 예산 측정 없이 기존 수치를 임의로 올리거나 내리지 않는다.

| 작업 | 창당 연결 상대 | 창당 세션 | 창당 전체 | 적용 지점 |
| --- | ---: | ---: | ---: | --- |
| 신규 쿠키 세션 발급 | 30 (`SESSION_ISSUE_CLIENT_HOURLY_LIMIT`) | — | 600 (`SESSION_ISSUE_GLOBAL_HOURLY_LIMIT`) | 유효한 기존 쿠키가 없는 세션 필요 요청 |
| 공개 뉴스 검색·원문·카드·키워드맵 작업 | 120 (`NEWS_SEARCH_CLIENT_HOURLY_LIMIT`) | — | 1200 (`NEWS_SEARCH_GLOBAL_HOURLY_LIMIT`) | 공급자 작업이 필요한 v1 뉴스·키워드맵 API(`GET /api/v1/keywords/map`), v2 뉴스맵 생성 |
| 뉴스맵 선정·확장 | 30 (`NEWS_MAP_CLIENT_HOURLY_LIMIT`) | — | 300 (`NEWS_MAP_GLOBAL_HOURLY_LIMIT`) | v1 graph/related, v2 뉴스맵 생성·분기 |
| 작업 제출 | 20 (`JOBS_CLIENT_HOURLY_LIMIT`) | 10 | 200 | `POST /jobs` |
| 리포트 신규 생성 | 10 (`REPORTS_CLIENT_HOURLY_LIMIT`) | 5 | 100 | v1 리포트 생성, v2 신규 리포트 작업 접수 |
| 전략 신규 생성 | 20 (`STRATEGIES_CLIENT_HOURLY_LIMIT`) | 10 | 200 | v1 전략 생성, v2 작업자의 신규 전략 생성 |
| 레거시 분석 | 20 (`ANALYZE_CLIENT_HOURLY_LIMIT`) | 10 | 200 | `POST /analyze` |

각 버킷의 **첫 허용 요청부터 3600초 고정 창**이다. 연결 상대는 애플리케이션에 직접 연결된 IP이며 IPv6 주소는 /64로 묶는다. 전달 헤더(`X-Forwarded-For`)를 요청자가 직접 보내도 버킷을 바꾸지 않는다. 프록시에서 원래 IP를 전달하려면 신뢰 프록시를 별도로 설정해야 한다. 모든 요청은 전체 한도를 함께 검사하므로 프록시 뒤에서 연결 상대 버킷이 공유되어도 전체 상한은 유지된다.

한도가 찬 요청은 공급자·작업 호출 전에 **429**를 반환하며 버킷을 추가로 차감하지 않는다. `Retry-After`는 막힌 버킷 중 가장 늦게 풀리는 버킷의 남은 시간을 올림한 양의 정수 초다. v2 JSON 오류 코드는 `RATE_LIMIT_EXCEEDED`이고 재시도 가능으로 표시한다. v1은 `detail` 형식을 유지한다. 브라우저의 교차 출처 응답에서도 `Retry-After`를 읽을 수 있다. Redis를 필수로 쓰는 환경에서 한도 저장소가 불가하면 차감이나 공급자 호출 없이 **503**을 반환하며 `Retry-After`를 보내지 않는다.

v2 `POST /api/v2/maps`는 검색과 맵 버킷을 **함께 예약**한다. 어느 한쪽이 찼으면 두 버킷 모두 차감하지 않는다. v2 `POST /api/v2/maps/{map_id}/branches`는 맵 버킷만 사용한다. 이미 저장된 기사를 읽는 v2 `GET /api/v2/news/{news_id}`와 저장된 맵·결과 조회, 작업 상태 폴링, v1 `GET /api/v1/keywords/map`의 유효한 프로세스 캐시 적중 및 공백 입력 검증 오류(422)는 공급자 작업 한도를 차감하지 않는다. 이미 허용된 요청이 이후 공급자 오류·검증 실패로 끝나더라도 예약된 사용량은 반환하지 않는다. v2 리포트의 동일한 `client_request_id` 재접수는 기존 작업을 돌려주고 신규 생성량을 차감하지 않는다.

클라이언트는 429 안내와 대기 시간을 표시하되 변경 요청을 자동 재전송하지 않는다. 사용자가 다시 실행할 때 `Retry-After`가 지난 뒤 요청한다. v2 전략 단계의 한도는 비동기 작업자에서 검사되므로 이 단계의 초과는 원래 접수 응답의 429가 아닌 작업 결과의 `STRATEGY_GENERATION_FAILED` 경고로 나타난다. 외부 뉴스 공급자의 429는 애플리케이션 한도 초과와 별개이며, 공급자 오류 계약에 따라 처리한다.

운영 수치 변경 전에는 실제 접속 IP 분포, 시간당 버킷 소진율, 429·503 빈도, 공급자 비용·상한, Redis 상태를 확인한다. 현재 기본값은 코드 정책이며 운영 배포·실제 키 사용 검증 완료를 뜻하지 않는다.
## v2 리포트 일일 실행 예산 (2026-10-26)

리포트 워커의 본문 획득(분류 확인 포함), RAG 조회, 분석, 활성화된 critic,
전략 생성의 실행 기회에 각각 1포인트를 예약한다. `V2_PROVIDER_DAILY_BUDGET_UNITS=1000`은
모든 v2 리포트 워커의 공유 일일 상한이며 Redis 시각 기준 KST 자정에 재설정한다.
`V2_PROVIDER_JOB_BUDGET_UNITS=32`는 같은 job의 재처리를 포함한 누적 상한이다.
일일/작업 장부는 Lua에서 함께 검사·예약한다. 거부 시 무차감이며 시작한 작업의 실패·취소·
불명확한 과금 결과는 환불하지 않는다. Redis 장애 시 추가 외부 작업을 거부한다.
메모리 장부는 기존 명시적 격리 개발 모드에만 사용한다.

본문/실패 캐시 및 완전 리포트/전략 재사용은 해당 작업 포인트를 소비하지 않는다.
다만 RAG 조회는 리포트 캐시 확인 전에 실행되므로 RAG on에서는 결과를 재사용해도
RAG 1포인트를 소비할 수 있다. 저장한 리포트의 전략 단계에서 소진되면 리포트 참조와
조회 권한을 보존하고 작업을 실패로 종료한다. 접수 후 오류는 GET 작업 HTTP 200의
`error`에 `DAILY_BUDGET_EXCEEDED`(다음 자정까지 `details.retry_after_seconds`),
`JOB_BUDGET_EXCEEDED` 또는 `BUDGET_UNAVAILABLE`로 기록한다.

이 정책은 **v2 리포트 실행량**을 제한한다. 실제 HTTP 시도 횟수·SDK 내부 재시도·
provider fallback·탐색/키워드/v1 경로·계정 전체 금액 상한을 계수하지 않는다.
일일 금액 한도 완료로 해석하면 안 된다. 운영 단가·usage와 전체 공급자 경계를 검증하는
후속 작업이 필요하다. 이 변경은 배포 필요이며 새 키/기본값을 김건에게 인계한다.
